## Rust: Record Sentry Issue Alert Slice

Part of epic 011. Port `internal/slices/recordsentryissuealert` and the shared event contracts (`internal/events`) to Rust, with the same behaviour as `docs/event-model.md` § "State change: record Sentry issue alert": size limit, signature, resource filter, validation, exception details and caps, and dedupe stream naming. Port the scenarios of `callback_test.go` as given/when/then tests, and add an integration test that posts a signed alert to the running app and finds the event in the store.

### Acceptance Criteria

- **Event contracts** (`src/events.rs`, `crate::events`): one type-name constant and one serde payload struct per event in `internal/events`, with no logic. That's `SentryIssueAlertReceived` (with `SentryStackFrame`) and the five investigation events with their skip reasons and failure stages, so 011.03 doesn't touch contracts. The JSON is identical to Go's: the same camelCase keys, and `culprit`, `exceptionType`, `exceptionValue` and `frames` are omitted when empty. A payload stored without them still decodes.
- **Slice** `src/slices/record_sentry_issue_alert/`, wired by `build.rs`, serving `POST /sentry/callback`. It runs the checks in Go's order, with the same status codes and bodies. Every response is `Content-Type: application/json`, and the body is Go's encoder output with its trailing newline:
  1. **Size.** A body over 10 MiB gets 413 `{"error":"body too large"}`. A body that can't be read gets 400 `{"error":"cannot read body"}`.
  2. **Signature.** `Sentry-Hook-Signature` must be the hex HMAC-SHA256 of the raw body, keyed with `SENTRY_CLIENT_SECRET`. It's compared in constant time and checked before decoding. A missing, non-hex, truncated or wrong signature gets 401 `{"error":"invalid signature"}`.
  3. **Resource.** Any `Sentry-Hook-Resource` other than exactly `event_alert` (missing, other, other case, trailing space) gets 200 `{"status":"ignored"}` and stores nothing.
  4. **Validation.** Malformed JSON, an empty body, a non-object, or a wrong field type (such as a numeric `issue_id` or a string `project`) gets 400 `{"error":"malformed event_alert payload"}`. A missing or blank `data.event.event_id`, `data.event.issue_id` or `data.triggered_rule` gets 400 `{"error":"event_id, issue_id and triggered_rule are required"}`. Values are stored as sent, not trimmed.
  5. **Exception details.** `culprit` is `data.event.culprit`. The exception fields come from the last (outermost) entry of `data.event.exception.values`, keeping at most the last 50 frames in Sentry's order. `culprit`, `exceptionType` and `exceptionValue` are capped at 2000 chars, and a frame's `file` and `function` at 500. A missing or unexpectedly shaped exception drops the details but still records the alert.
  6. **Dedupe.** The event goes to stream `sentry-issue-alert-<hex sha256(event_id + "\x00" + triggered_rule)>`, appended at expected version 0. On success: 200 `{"status":"recorded"}`. A redelivery's conflict gets 200 `{"status":"duplicate"}` and stores nothing. The same event triggering another rule is a new alert.
  7. **Store failure.** Any other store error gets 500 `{"error":"internal error"}`, with no details in the body, and logs ERROR "record sentry issue alert" with an `error` field.
- **Config.** The factory reads `SENTRY_CLIENT_SECRET`. If it's missing or empty, it fails with "SENTRY_CLIENT_SECRET must be set", so the binary logs "invalid configuration" and exits 2.
- **Tests.**
  - Every `callback_test.go` and `config_test.go` scenario is ported as a readable given/when/then test, with a payload fixture matching Go's.
  - An integration test in `tests/` runs the app on `127.0.0.1:0`, posts a signed alert, gets 200 `{"status":"recorded"}`, and finds the event in the store.
  - `tests/cli.rs` covers exit 2 with "invalid configuration" when `SENTRY_CLIENT_SECRET` is missing.
- The Go code stays untouched and keeps passing.

## Implementation Plan

### TLDR

Add `crate::events` (pure serde contracts), then the slice as one axum handler over the raw request (`Request` → limited body bytes → signature → resource → decode → validate → append), with tests driving the handler through the app's router shape and an end-to-end test against the real `app::run`.

### Steps

1. **Contracts.** `src/events.rs`, `pub mod events` in `lib.rs`. Mirror `internal/events/events.go` one to one: `SENTRY_ISSUE_ALERT_RECEIVED` style constants for every type name, skip reasons and failure stages (keep them `&str` constants, not enums, so the stored strings stay obviously Go's); payload structs with `#[serde(rename_all = "camelCase")]` and snake_case fields, so `pr_url` → `prUrl` and `web_url` → `webUrl` match Go's tags without per-field renames. Optional fields are `String`/`Vec` with `#[serde(default, skip_serializing_if = "…is_empty")]`, so empty means omitted and old payloads decode. `project` is `i64`, frame `line` is `i64`. Check: a unit test that serialises a full and a minimal alert to the exact Go JSON and decodes Go's "old payload" string.
2. **Config.** The factory reads `SENTRY_CLIENT_SECRET` via `deps.getenv`; `None` or `""` is a typed error whose `Display` is exactly `SENTRY_CLIENT_SECRET must be set`. Route: `MethodFilter::POST`, `/sentry/callback`.
3. **Body and size.** Take `axum::extract::Request` (no `Bytes`/`Json` extractors: their rejections and axum's 2 MB default limit would change the 413/400 bodies). Read with `http_body_util::Limited` at `10 << 20` and `BodyExt::collect`; a `LengthLimitError` (downcast the boxed error) → 413, any other read error → 400 "cannot read body". Exactly 10 MiB must pass. Add `http-body-util` with `cargo add`.
4. **Signature.** Hex-decode the header (missing or invalid header value → invalid), then `Hmac<Sha256>::verify_slice`. Runs before any JSON parsing (`TestSignatureIsCheckedBeforeDecoding`).
5. **Resource, decode, validate.** Header must equal `event_alert` byte for byte. Decode into private serde structs mirroring Go's `webhook`: every field `#[serde(default)]` so missing keys and `null` give empty values (Go's zero values), while wrong types fail the whole decode → 400 "malformed event_alert payload". Keep `exception` as an optional `serde_json::Value` (or `RawValue`) decoded separately and leniently, so a bad shape drops the details only. Blank = `trim().is_empty()`.
6. **Exception details and caps.** Last entry of `values`, last 50 frames, char-based truncation (2000 / 500), same as `exception.go`. Inside the lenient decode, `null` for a nested field is empty, not an error, as in Go.
7. **Append and respond.** Stream id per the ACs; `store.append(id, 0, …)`; `eventstore::Error::Conflict` → duplicate, other errors → `tracing::error!(error = %err, "record sentry issue alert")` and 500. Responses: one helper writing status, `Content-Type: application/json` exactly (not with `charset`) and `serde_json::to_vec(body)` + `\n`.
8. **Slice tests** (in the slice dir, `#[cfg(test)]`). Build the slice's `StateChange` from the real factory with a test getenv, turn it into an `axum::Router` with `tower::ServiceExt::oneshot`-style calls (add `tower` as a dev-dependency if `oneshot` isn't reachable otherwise), backed by a temp-dir `Store`. Port each Go test as `given_…_when_…_then_…` (or a module per scenario), including all table cases (5 bad signatures, 6 resources, 12 invalid bodies) as loops with the case name in the assertion message. The fixture is Go's `eventAlertFixture` verbatim (a `const` or `include_str!` of a file next to the tests; the guard allows relative `include_str!`). Assert full response bodies, not just status, since the bodies are part of the contract. Store failure: call `store.close()` before posting; also assert the ERROR log line using a local `tracing_subscriber` capture (`crate::testlog` is off-limits to slices under the guard).
9. **End-to-end** (`tests/`): build slices from `underling::slices::FACTORIES` with a getenv that supplies the secret, run `app::run` on `127.0.0.1:0` with a temp data dir, POST a signed alert with `reqwest`, expect 200 `{"status":"recorded"}\n`, cancel, await a clean `Ok(())`, then reopen the store from the data dir and find exactly one `SentryIssueAlertReceived` with the expected stream id.
10. **CLI.** In `tests/cli.rs`, spawn with `env_remove("SENTRY_CLIENT_SECRET")` → log "invalid configuration" whose `error` names the variable, exit 2. The existing SIGTERM test must now set `SENTRY_CLIENT_SECRET`, or it exits 2 before "app started".

### Notes

- Go's `json.Unmarshal` matches keys case-insensitively and replaces invalid UTF-8 with U+FFFD; serde does neither. Sentry sends exact lowercase keys and valid UTF-8, so accept the difference and record it in Implementation Notes.
- The stored payload is a `serde_json::Value` (sorted keys); key order isn't part of the contract.
- Go's 413 also sets `Connection: close`; not part of the contract.

## Implementation Notes

- **Contracts.** `src/events.rs` mirrors `internal/events` with `&str` constants (`SENTRY_ISSUE_ALERT_RECEIVED`, `SENTRY_ISSUE_INVESTIGATION_*`, `INVESTIGATION_SKIPPED_*`, `INVESTIGATION_FAILED_*`) and serde structs. Every struct derives `Default`, so a minimal one can be built with `..Default::default()`. 011.03 needs no contract changes.
- **Go's decoding rules (`go_json.rs`), a surprise.** serde's derive accepts a JSON array for a struct (fields by position) and rejects `null` for a `String`. Go does the opposite. So `[]` would have passed as an empty webhook with the "required" error instead of "malformed", and `"title": null` would have rejected the alert. The slice decodes structs through a small `Object<T>` visitor (an object, or empty from `null`; anything else is an error) and scalars and lists through `null_as_default`. That covers the top-level body, `data`, `data.event` and the exception's nested structs. Tests cover `[]`, `{"data":[]}`, an array event, a `null` body, `null` data, a `null` issue id and `null` optional fields.
- **Decoded straight from the body (review fix).** The first version went through `serde_json::Value`, which parses every value, ignored or not. So a lone surrogate (`"\udc00"`), invalid UTF-8 or nesting deeper than 128 in a field the slice ignores got a 400 where Go records the alert. `Object<T>` is now a visitor (`deserialize_any`; `visit_map` hands the map to `T` via `MapAccessDeserializer`), so ignored fields are only skipped. serde_json skips without decoding strings and without a depth limit (its `ignore_value` is iterative). Tests: each of the three in an ignored event field is recorded.
- **The exception is a second pass over the body,** reading only `data.event.exception` (`exception::details(&body)`). Any failure there drops the details, never the alert. I chose this over the suggested `Option<Box<RawValue>>`: a probe showed that capturing a `RawValue` still fails the whole decode on invalid UTF-8 inside it, so the alert would be rejected. The second pass costs a re-parse of at most 10 MiB, which is fine at webhook rates. Tests: invalid UTF-8 in the exception `type` records the alert without details, and nesting deeper than 128 in an ignored field inside an exception value keeps the details.
- **Lone surrogate escapes become U+FFFD (review fix).** Sentry sends them: a JS message cut mid-emoji keeps half a UTF-16 pair, and Python's `json` writes it as an `\udXXX` escape. serde_json rejects such escapes, so the alert would have been lost for good. After the signature check and before decoding, `go_json::replace_lone_surrogates` rewrites every unpaired `\ud800`–`\udfff` escape inside a string to `\ufffd`, as Go's decoder does. It's a small byte scanner that tracks strings, copies other escapes whole (so `"\\udc00"` is left alone) and keeps valid pairs. Both passes read the rewritten body, so an exception keeps its details, with U+FFFD as in Go (`"A�"`). The signature is still verified over the bytes as sent. Tests cover the scanner directly and, through the slice, the title, the exception, a valid pair, an escaped backslash and the signature over the original bytes.
- **The body is read raw.** `Limited` plus `collect` runs on the request body, and a `LengthLimitError` gives 413. A unit test checks that a body of exactly 10 MiB is accepted. Through the real app (`tests/sentry_alert.rs`): a 3 MiB alert is recorded (so no axum 2 MB `DefaultBodyLimit` applies), an alert over 10 MiB gets 413 `{"error":"body too large"}\n`, and a raw TCP request with `Content-Length: 100`, a shorter body and a write half-close gets 400 `{"error":"cannot read body"}\n`.
- **Tests call the handler directly.** `Callback::record` runs on a hand-built `Request`, with no router. `StateChange::into_route` is private to `app`, and adding a test hook there wasn't worth it. The config tests check the route's method and path, and `tests/sentry_alert.rs` covers the real wiring through `app::run`. `tower` was added as a dev-dependency but turned out to be unneeded, so it was removed again.
- **Log capture.** The store-failure test asserts the ERROR "record sentry issue alert" line (`error` = "event store is closed") with a small local `tracing_subscriber` capture, since the guard keeps slices out of `crate::testlog`.
- **CLI.** `underling()` in `tests/cli.rs` now sets `SENTRY_CLIENT_SECRET`, so the SIGTERM test still reaches "app started". The new test removes it and expects "invalid configuration" with `error` = "SENTRY_CLIENT_SECRET must be set", then exit 2.
- **Mutation checks** (each one killed by at least one test):
  - accepting any signature; another resource string;
  - letting `Object` accept arrays or reject `null`; `null_as_default` rejecting `null`;
  - frame and text caps off by one; first instead of last exception; not capping the culprit;
  - another stream separator; appending at expected version 1; dropping the conflict branch;
  - a body limit one byte short; a 2 MB body limit; swapping the 413 and "cannot read body" replies;
  - validating without trimming; dropping the trailing newline;
  - decoding the body, or the exception pass, through `serde_json::Value`.
  - not rewriting lone surrogates; verifying the signature over the rewritten body; never recognising a pair, or taking two low surrogates for one; copying one byte of an escape instead of two; ignoring string boundaries.
- **Accepted deviations from Go.** Sentry sends exact lowercase keys, valid UTF-8, no duplicate keys and integer ids, so none of these matter in practice:
  - **Key case.** Go matches keys case-insensitively (`"Event_ID"` fills `event_id`); serde doesn't, so such a key is ignored.
  - **Invalid UTF-8** in a field the slice reads: Go replaces it with U+FFFD and records the alert. serde_json rejects it: 400 in the top-level fields, details dropped in the exception. In ignored fields both accept it. Raw invalid UTF-8 is rarer than lone surrogate escapes (JSON encoders escape or replace it), so it stays a deviation.
  - **Duplicate keys.** Go lets the last scalar win and merges repeated objects field by field. serde's derive rejects a repeated field it reads: 400 "malformed event_alert payload" in the top-level fields (e.g. two `event_id`s, or `data` twice), details dropped in the exception. Repeated ignored keys are fine. (The first version's `Value` step happened to make the last value win, so the earlier note here was wrong for it. It is right again now.)
  - **`-0` as an integer.** Go reads `-0` as 0. serde_json parses it as a float, so `"project":-0` gets 400 and a `"lineno":-0` drops the details.
  - **Nesting limit.** Go's decoder rejects JSON nested deeper than 10000 levels; Rust accepts any depth. Ignored values are skipped iteratively without a limit, and the fields the slice reads sit at most a few levels deep, so serde_json's 128 limit never applies.
  - **Stored payload bytes.** The payload is stored as a `serde_json::Value`, so keys are sorted instead of in Go's struct order. serde_json also doesn't HTML-escape `<`, `>`, `&`, U+2028 or U+2029 the way Go's `json.Marshal` does. The decoded JSON is identical.
  - **413 reason phrase.** hyper writes `413 Payload Too Large`, Go's net/http writes `413 Request Entity Too Large`. Status code and body match. Go also adds `Connection: close` there.
